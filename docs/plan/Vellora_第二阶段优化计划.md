# Vellora 第二阶段优化计划：整体构图与交互完成度

> 实施基线：用户本地已经完成的第一阶段界面及当前未提交工作区。
> 文档用途：交给本地 Agent 执行第二阶段优化；本文是后续计划，不代表这些优化或验收已经完成。
> 工作目录：`G:\mirad\mirad-server\md`，以本地实际仓库位置为准。

这一阶段沿用已经确定的中性色、系统无衬线字体、尺寸规范和功能布局，重点把各个部分组合成一个完成度更高的编辑器：工具栏有清楚的主次，控件像同一套产品，状态切换稳定，复杂文档也保持舒服的阅读效果。

计划将“查看当前实景、筛选实际问题”作为第一步，已经达标的部分直接沿用。

## 一、目标与实施原则

以上一轮已完成的本地工作区为基线，进行第二轮视觉评审和针对性优化。

本轮目标：

1. 完善工具栏、文件信息、正文、目录和浮层之间的视觉主次。
2. 统一按钮、图标、文字、选中态和间距的细节。
3. 优化保存、搜索、目录开合及错误出现时的界面稳定性。
4. 完成复杂文档、窄窗口和缩放环境下的表现收敛。

**允许为达到上述目标调整展示层 DOM、控件分组和组件内部布局，并新增必要的小型展示组件。** 按组件完成影响分析后增量实施，以效果和可维护性决定改动范围。

继续沿用上一轮的技术与产品边界：

- 使用 React 和原生 CSS，沿用浅色模式、系统字体、Vellora 图标和原生窗口标题栏。
- 保留现有编辑器、Tauri 命令、保存流程和功能集合。
- 对外 API、文件格式、会话状态及编辑器接口保持兼容。
- 不引入 Open Claude UI 整包、Tailwind、Framer Motion 或 Electron。
- 不增加主题设置、格式工具栏或其他产品能力。
- 以当前未提交工作区为基线，保留其他任务的改动，不创建分支，不执行提交、打包安装器或发布。
- 所有拟修改组件在编辑前重新进行影响分析；如果 GitNexus 返回 UNKNOWN，结合当前源码调用关系核对，不将 UNKNOWN 视为低风险结论。

## 二、先建立本轮基线，确定实际优化项

### 1. 读取当前实现与实施记录

在本地仓库中先查看：

- 当前工作区和暂存区差异，以及新增但尚未跟踪的文件。
- 上一轮的 `FRONTEND_DESIGN_PACK.md`。
- 实际修改后的工具栏、目录、搜索、弹窗和样式实现。
- 上一轮测试结果、截图和已记录的遗留问题。

依赖环境已经可用时直接复用；只有依赖缺失或锁文件发生变化时，才重新恢复依赖。

### 2. 以真实窗口确定问题

先以 **820×900 的默认窗口**观察完整界面，优先检查：

- 正常文档阅读。
- 源码编辑与搜索。
- 目录打开。
- 未保存确认或保存错误。

上一轮截图如果与当前代码一致，可以复用；发生变化的场景重新截图。

**先列出最多五个最影响完成度的问题，并排序。** 每个问题都写清楚：

| 项目 | 记录内容 |
|---|---|
| 实际表现 | 当前截图中能观察到什么 |
| 影响 | 为什么影响主次、阅读、操作或稳定性 |
| 改动范围 | 涉及哪些展示组件与样式 |
| 预期结果 | 修改后应该有什么可见变化 |
| 验收场景 | 用哪个窗口尺寸、文档和操作验证 |

不要为了填满清单而修改已经协调的部分。

## 三、优先完成整屏构图与控件主次

这是第二阶段最重要的一批工作。

### 1. 完善顶部工具栏的整体关系

在上一轮布局基础上，检查并调整以下关系：

- 左侧文件信息形成稳定的信息区域，长文件名出现时不挤压模式切换和右侧操作。
- 中间模式控件有清楚的选中状态，并与两侧区域保持协调。
- 右侧保存、查找、目录形成一个有秩序的操作组。
- 文件状态变化时，工具栏主要控件的位置保持稳定。
- 工具栏切换为两行后，文件信息与操作区仍然有明确的阅读顺序。

重点检查：**文件名、当前模式和保存操作是否容易识别，同时正文仍然是整个窗口的视觉主体。**

可以调整分组、间距、对齐方式和展示结构，不必拘泥于第一轮的 DOM 组织方式。

### 2. 完成按钮的角色区分

在现有控件尺寸上建立少量清晰的视觉角色：

| 角色 | 本轮优化目标 |
|---|---|
| 主要操作 | 有修改可保存时，保存按钮具有清楚的操作权重；保存中的反馈不改变按钮宽度 |
| 常用操作 | “打开”容易发现，与右侧主要操作保持适当区分 |
| 工具操作 | 查找、目录采用统一的轻量按钮，普通状态与面板已打开状态可区分 |
| 模式选择 | 轨道、滑块、文字形成完整控件，选中态在关闭动效后仍然明确 |
| 危险操作 | 通过文字、位置和视觉样式表达后果，与普通确认操作区分 |

沿用现有保存与查找入口。按钮是否可用，继续由当前业务状态决定。

### 3. 完成图标与文字的光学对齐

统一检查：

- 图标的实际视觉大小、线条粗细和重心。
- 图标与文字之间的距离。
- 按钮文字的垂直位置。
- 分段滑块四周留边。
- 文件名、状态、目录条目和弹窗标题的字重关系。
- 不同组件里承担同一角色的文字是否使用同一字号、行高和颜色。

这里以真实渲染效果为准。相同的 SVG 外框尺寸，也需要观察图形本身是否显得过大、过小或偏移。

**本批交付：默认窗口的完整视觉样板，以及相同场景的前后对比截图。**

## 四、完善状态变化的稳定性和浮层协作

这一批着重解决使用过程中出现的跳动、遮挡和焦点不连贯。

### 1. 保存与错误反馈

检查以下连续操作：

> 编辑内容 → 点击保存 → 保存中 → 保存成功或失败 → 继续编辑／再次保存。

优化目标：

- 保存状态变化时，按钮和相邻工具的位置稳定。
- 保存失败的详细信息完整显示，同时保持主要操作可见。
- 错误反馈出现、换行或消失时，搜索浮层的位置正确。
- 阅读模式中正在直接编辑的内容，仍然进入现有保存流程。
- 状态文字与颜色表达一致，必要信息具有足够可读性。

优先使用已经存在的状态。加载和反馈的显示时机跟随真实操作结果。

### 2. 搜索与顶部反馈区域

统一浮层的定位基准，明确工具栏、第二行文件信息和错误反馈区之间的关系。

需要验证：

- 单行和双行工具栏下，搜索位置都正确。
- 长错误显示时，搜索不会覆盖必须阅读的反馈。
- 搜索导航行展开后，正文区域和其他控件没有不必要的位移。
- 输入、计数、上下项和关闭按钮之间的对齐保持稳定。
- 打开搜索、切换模式、继续输入后，高亮与实际文字仍然重合。

### 3. 目录、搜索和确认弹窗的交互顺序

沿用现有交互优先级，重点验证多种界面状态组合时的行为。

目录关闭需要按原因分别处理：

- **Escape 关闭**：按约定恢复目录按钮焦点。
- **点击外部关闭**：保留目标位置原本的点击行为。
- **选择标题关闭**：完成标题定位，避免焦点恢复引起额外滚动。
- **跨越停靠断点**：保持目录开关状态和当前标题，不意外重新初始化。

确认弹窗出现后，由弹窗管理当前交互；关闭时恢复到合理位置。输入法选词和编辑器已经处理的 Escape，不应继续触发其他界面关闭。

### 4. 动效服务于状态变化

沿用上一轮的动效时间，针对实际表现优化：

- 滑块移动时文字保持稳定。
- 浮层进入时清楚、轻量。
- 展开和收起不产生结束瞬间的跳变。
- 操作结果及时呈现，动画不延迟保存或关闭。
- 减少动态效果模式下，所有状态仍然清楚，操作保持即时。

**本批交付：关键操作前后的状态截图，以及实际操作验证结果。**

## 五、完成正文节奏和复杂内容的打磨

上一轮已经完成字号、行高和基本排版，本轮重点看这些规则组合到真实文档后的效果。

### 1. 检查首屏与连续阅读节奏

使用包含标题、段落、列表、引用和代码的真实文档，检查：

- 首标题与正文顶部距离是否自然。
- 标题、说明段落和后续内容的间距是否协调。
- 连续多个标题时，层级是否仍然清楚。
- 列表内部和列表前后的留白是否一致。
- 引用、表格和代码块是否与普通正文形成合理区分。
- 短文和长文都保持合适的空间感。

如果需要调整，优先修改对应的排版规则，避免针对某一份样例文档添加特殊样式。

### 2. 使用一份固定的综合验收文档

至少包含：

- 长中文文件名。
- 多级标题和较长目录项。
- 中英文混排、链接和行内代码。
- 嵌套列表、引用、宽表格。
- 长代码行、制表符和多个搜索匹配。
- 正常图片与图片缺失状态。

表格和代码的横向滚动继续限制在自身区域内。源码编辑器与搜索覆盖层共同核对字体、行高、字距、制表符宽度、换行方式、可用宽度和内边距。

涉及内容容器的改动，需要核对快速编辑依赖的标记、事件和源码范围映射。

### 3. 完善空白、加载与失败页面的构图

使用现有 Vellora 图标和功能文案，检查图标、标题、说明和操作按钮是否形成完整组合。

关注默认窗口中的位置、间距和视觉重心；长错误能够换行，状态转换后页面不出现突兀的空间变化。

**本批交付：综合文档的阅读、源码和搜索效果，以及必要状态的真实截图。**

## 六、验证顺序与完成标准

### 1. 分批验证

按以下顺序实施：

1. **整屏构图与控件主次。**
2. **状态反馈与浮层协作。**
3. **复杂文档和窗口适配。**

每批只验证相关的行为与渲染结果。完成三批后，再运行上一轮约定的最终门禁：

```text
npm run typecheck
npm test
npm run test:rust
npm run build:web
```

复用已有行为测试；只有本轮新增或改变了交互行为，才补充必要回归覆盖。颜色、间距、阴影和图标位置通过真实渲染验收。

区分已有失败与本轮新增失败，并记录实际执行结果。真实 Tauri 窗口渲染与操作验证完成后，才能判定相应验收项完成。

### 2. 重点场景

| 场景 | 重点 |
|---|---|
| 820×900 默认窗口 | 整屏构图、主要操作、正文首屏 |
| 640px 窄窗口 | 两行工具栏、浮动目录、搜索和长文件名 |
| 760px 附近 | 工具栏切换时的对齐与浮层定位 |
| 1024px 附近 | 目录浮动与停靠转换、阅读位置和当前标题 |
| 1280×900 | 宽窗口中的比例、留白和内容位置 |
| 保存错误与搜索同时出现 | 反馈可读、浮层不遮挡、操作仍然可用 |

记录截图的内容区尺寸、系统缩放和测试文档，使前后对比具有一致条件。浏览器辅助检查与真实 Tauri 窗口验收分别记录。

### 3. 最后做一次整体视觉复审

首轮修改完成后，对照同场景截图检查：

- 主次是否更清楚。
- 控件是否更一致。
- 阅读节奏是否更自然。
- 状态变化是否更稳定。
- 默认、窄窗和复杂状态下是否都保持完整。

发现明确问题后做针对性修订；已经达到目标的区域及时收敛。
